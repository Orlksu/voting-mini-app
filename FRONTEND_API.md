# 📖 Полное Руководство по API для Фронтенда (Frontend API Guide)

Этот документ содержит все реальные юзкейсы, примеры JSON и скрытые нюансы, чтобы у фронтенда не возникло ни единого вопроса при интеграции.

---

## ⚡ Главные концепции (Обязательно к прочтению)

1. **Асинхронность (Polling)**
   Все тяжелые операции (расчет маршрутов, парсинг CSV) отдают `HTTP 202 Accepted` и объект `{ "jobId": "uuid" }`. Фронтенд должен раз в 1-2 секунды дергать ручку проверки статуса (`GET /api/v1/optimization/jobs/{jobId}`), пока поле `status` не станет `Completed` (или `Failed`).
2. **Машина Времени (Time-Travel)**
   Если на UI есть ползунок времени (симулятор дня), **всегда** передавайте его значение в параметр `?currentTime=2026-10-25T14:00:00Z` при любых мутациях (отключение инженера, удаление заявки, перепланирование). Если не передать, бэкенд использует реальное серверное время.
3. **Идентификаторы (id)**
   Бэкенд всеяден. В URL (`/engineers/{id}`) можно передавать как внутренний UUID (`550e8400-e29b-...`), так и ваш строковый `ExternalId` (например, `ENG-01`).

---

## 📚 Важные Словари (Enums)

Бэкенд ожидает и возвращает следующие значения (в JSON можно передавать строками или цифрами, но строки надежнее для понимания):

* **Статус заявки (OrderStatus):** 
  `NotDispatched` (0 - Серая на карте), `Dispatched` (1 - Назначена), `InProgress` (2 - В работе), `Completed` (3 - Готова), `Cancelled` (4 - Отменена).
* **Скиллы (SkillType):** 
  `LocalRepair` (1 - Ремонт), `Installation` (2 - Монтаж), `Emergency` (3 - Авария).
* **Приоритет (OrderPriority):** 
  `Low` (1), `Normal` (2), `High` (3), `Emergency` (4).
* **Транспорт (TransportType):** 
  `Pedestrian` (1 - Пешком/Общественный), `Car` (2 - Автомобиль).

---

## 🛠 Сценарий 1: Загрузка исходных данных (CSV)

1. **Отправляем файл** (`multipart/form-data`, поле `file`):
   * `POST /api/v1/engineers/upload-csv`
   * `POST /api/v1/work-orders/upload-csv`
2. **Ждем результат (Polling):** `GET /api/v1/engineers/import-jobs/{jobId}`
   * *Для UI:* Выводите прогресс-бар из полей `processed` и `total`.

---

## 🗺 Сценарий 2: Отрисовка списков и карты

1. **Инженеры:** `GET /api/v1/engineers`
   * Даст массив инженеров с их `startLatitude` и `startLongitude` для стартовых маркеров.
2. **Заявки:** `GET /api/v1/work-orders`
   * Возвращает все точки. Фильтруйте по `status` (отрисовывайте `NotDispatched` серым цветом).

---

## 🚀 Сценарий 3: Основной расчет маршрутов (Replan)

**Когда нужно:** Диспетчер нажимает "Рассчитать".

1. **Запуск:** `POST /api/v1/optimization/replan?currentTime={значение_ползунка}`
   * Тело запроса пустое. Бэкенд сам соберет всех свободных инженеров и все заявки в статусе `NotDispatched` (или брошенные заявки).
2. **Polling:** `GET /api/v1/optimization/jobs/{jobId}`
3. **Получение результата:** `GET /api/v1/optimization/jobs/{jobId}/result`
   * Возвращает итоговые `routes` (маршруты инженеров).
4. **Как рисовать линии на карте:**
   В каждом маршруте есть поле `encodedPolyline`. Это сжатая кривая (алгоритм Google Encoded Polyline). Используйте npm-пакет `polyline` (или плагины Leaflet/GoogleMaps), чтобы раскодировать строку в точки `[lat, lng]` и нарисовать реальный путь по дорогам!

---

## 🚑 Сценарий 4: Экстренная заявка (Молния)

**Когда нужно:** Срочно внедрить аварийную заявку, "растолкав" обычные.

1. **Запуск:** `POST /api/v1/optimization/emergency`
2. **Тело запроса (Пример JSON):**
```json
{
  "eventTime": "2026-10-25T14:30:00Z", // Значение ползунка симулятора
  "urgentOrder": {
    "externalId": "SOS-001", // Ваш уникальный ID
    "address": "г. Москва, ул. Ленина, д. 10", // Обязательно
    "latitude": null,  // Магия: Оставьте null, бэкенд сам найдет координаты (Nominatim)!
    "longitude": null,
    "durationMinutes": 60,
    "requiredSkill": "Emergency", // Или цифра 3
    "priority": "Emergency",      // Или цифра 4
    "taskType": "Обрыв оптоволокна"
  }
}
```
3. **Что делает бэкенд:** Геокодирует адрес, создает заявку, запускает алгоритм, который бросает ближайшего свободного инженера на аварию. Те заявки, которые он не успеет сделать из-за этого, упадут обратно в `NotDispatched` с причиной `EmergencyDisplaced`. Фронт просто делает Polling как обычно.

---

## 🔧 Сценарий 5: Инженер сломался / Временно недоступен

**Когда нужно:** Клик по тумблеру "Доступен" в карточке инженера.

1. **Запуск:** `PATCH /api/v1/engineers/{id}/availability?isAvailable=false&currentTime={значение_ползунка}`
   * *Тела запроса нет.*
2. **Поведение:** Бэкенд мгновенно отвяжет от инженера все заявки, до которых он **еще не доехал** (сравнивая их `ServiceEnd` с вашим `currentTime`).
3. **Обновление UI:** Дерните `GET /api/v1/work-orders` — вы увидите, что его будущие заявки стали `NotDispatched` (серыми). Подсветите диспетчеру кнопку "Перепланировать" (Сценарий 3).

---

## 🗑 Сценарий 6: Клиент отменил заявку

**Когда нужно:** Клик по крестику на заявке.

1. **Запуск:** `DELETE /api/v1/work-orders/{id}`
2. **Поведение:** Заявка получит статус `Cancelled`. Если она была у кого-то в маршруте, бэкенд **автоматически (в фоне) запустит перепланирование**, чтобы уплотнить график этого инженера.
3. **Ответ ручки:** Вернет HTTP 202 и `{ "jobId": "..." }`. Просто начните пуллить этот джоб, и когда он завершится — обновите маршруты на экране.
