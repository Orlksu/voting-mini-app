# 🎯 Полное Техническое Руководство для Фронтенда (Frontend Tasks & API)

Этот документ содержит полное описание всех 11 функциональных модулей фронтенда с примерами данных, эндпоинтами и правилами отображения.

---

## 1. Загрузка инженеров (CSV)

**Задача UI:** Компонент Drag-and-drop / кнопка выбора файла для загрузки списка полевых инженеров.

* **Эндпоинт отправки:** `POST /api/v1/engineers/upload-csv`
* **Формат:** `multipart/form-data`, поле формы `file`.
* **Ответ сервера (202 Accepted):**
  ```json
  {
    "jobId": "3fa85f64-5717-4562-b3fc-2c963f66afa6"
  }
  ```
* **Поллинг прогресса:** раз в секунду опрашивать `GET /api/v1/engineers/import-jobs/{jobId}`
  * Ответ:
    ```json
    {
      "jobId": "...",
      "status": "Running", // "Completed" | "Failed"
      "stage": "Геокодирование адресов...",
      "processed": 14,
      "total": 30
    }
    ```
  * При `status === "Completed"` скрывать прогресс-бар и обновлять список инженеров на экране (`GET /api/v1/engineers`).

## 2. Отмена и завершение заявок

**Задача UI:** В карточке заявки и в попапе маркера на карте добавить две кнопки: «Отменить» и «Завершить».

### А. Отмена заявки клиентом/диспетчером
* **Эндпоинт:** `DELETE /api/v1/work-orders/{id}` *(или `/api/v1/workorders/{id}`)*
  * `{id}` — это `Guid` или строковый `ExternalId` заявки.
* **Тело запроса (JSON):**
  ```json
  {
    "reason": "Клиент перенес встречу на другой день"
  }
  ```
* **Что происходит:**
  * Заявка получает статус `Cancelled`.
  * Если она была в маршруте инженера, бэкенд **автоматически запустит перепланирование** и вернет в ответе `replanJobId`.
  * Фронтенд начинает опрашивать `GET /api/v1/optimization/jobs/{replanJobId}`, чтобы обновить нити маршрутов инженера (он поедет дальше без простоя).

### Б. Отметка заявки как выполненной
* **Эндпоинт:** `POST /api/v1/work-orders/{id}/complete`
* **Тело запроса:** отсутствует.
* **Что происходит:** Статус заявки в БД переходит в `Completed`. Маркер на карте красится в зеленый цвет.

## 3. Добавление отдельной заявки вручную

**Задача UI:** Форма с полями: Адрес, Тип работ, Время начала/конца окна, Приоритет, Длительность (минуты), Необходимый транспорт.

* **Эндпоинт:** `POST /api/v1/work-orders`
* **Тело запроса (JSON):**
  ```json
  {
    "externalId": "ORD-MANUAL-01",
    "address": "г. Москва, ул. Арбат, 15",
    "latitude": null,
    "longitude": null,
    "district": "Центральный",
    "windowStart": "2026-10-25T10:00:00Z",
    "windowEnd": "2026-10-25T14:00:00Z",
    "requiredSkill": "Installation", // LocalRepair | Installation | Emergency
    "priority": "High",              // Low | Normal | High | Emergency
    "durationMinutes": 60,
    "taskType": "Подключение клиента",
    "requiredTransport": "Car"       // Car | PublicTransit | Bicycle | Pedestrian | null
  }
  ```
* **Нюанс:** Поля `latitude` и `longitude` можно оставить `null` — бэкенд автоматически геокодирует адрес через Nominatim.

## 4. Информация по офисам (депо)

**Задача UI:** Карточки/выпадающий список офисов депо, отображение депо на карте (иконка базы/дома).

* **Эндпоинт:** `GET /api/v1/depots`
* **Формат ответа:**
  ```json
  [
    {
      "id": "c2b53a47-...",
      "name": "Основное депо Восток",
      "address": "г. Москва, Симферопольский проезд, д. 7",
      "latitude": 55.679643,
      "longitude": 37.616335,
      "district": "Южнопортовый"
    }
  ]
  ```
* **Как связать:** У каждого инженера (`GET /api/v1/engineers`) и заявки есть поле `depotId`. По клику на депо можно фильтровать инженеров и заявки данного филиала.

## 5. Нумерация точек на карте (Sequence)

**Задача UI:** Показать очередность объезда: на маркерах на карте должны отображаться цифры 1, 2, 3...

* **Откуда брать данные:** Из рассчитанного маршрута `GET /api/v1/optimization/jobs/{jobId}/result` или `GET /api/v1/engineers/{id}/route`.
* В объекте `stops` для каждой остановки приходит поле **`sequence`**:
  ```json
  {
    "sequence": 1,
    "externalOrderId": "ORD-101",
    "address": "ул. Тверская, 7",
    "latitude": 55.7576,
    "longitude": 37.6111
  }
  ```
* **Отрисовка:** Рендерите кастомный SVG-маркер (или круглый бейдж) с цифрой `stop.sequence` внутри.

## 6. Вывод причины назначения (Assignment Reason)

**Задача ТЗ:** Объяснимость решений алгоритма оптимизации.

### А. Для назначенных заявок (Route Stops)
В каждой остановке маршрута (`RouteStopDto`) бэкенд возвращает готовый понятный человеку текст в поле **`assignmentReason`**:
* **Пример:**
  > *"Назначен Иван Смирнов (Car): квалификация Installation, доезд 12 мин (4.2 км)"*
* **Где показывать:** В tooltip маркера на карте и в карточке заявки в панели инженера.

### Б. Для неназначенных заявок (Unassigned Orders)
В ответе оптимизации в массиве `unassignedOrders` приходят поля:
* `reasonCode`: Код причины (например, `TimeWindowMissed`, `NoQualifiedEngineer`, `ShiftDurationExceeded`).
* `reasonDescription`: Человеческое пояснение (например: *"Нет инженеров с квалификацией Emergency в этом районе"* или *"Смена инженеров заканчивается раньше времени доставки"*).
* **Где показывать:** В отдельной вкладке «Нераспределенные заявки» в виде предупреждающего бейджа.

## 7. Поиск и фильтрация заявок

**Задача UI:** Поисковая строка над таблицей/списком заявок.

### А. Локальный мгновенный поиск (Клиентский)
Рекомендуется для быстрого UI. Получаете полный список через `GET /api/v1/work-orders` и фильтруете в памяти React/Vue по:
* Номеру заявки (`externalId`);
* Адресу (`address`);
* Статусу (`status`: 0 — NotDispatched, 1 — Dispatched, 2 — InProgress, 3 — Completed, 4 — Cancelled);
* Району (`district`).

### Б. Серверный поиск по ID
* `GET /api/v1/work-orders/{id}?district={optional}`

## 8. Точный расчетный интервал работы (Service Window)

**Задача UI:** Показывать, в какое именно время инженер будет выполнять работы на адресе, а не только исходное широкое окно клиента.

* **В карточке нераспределенной заявки (`status === 0`):**
  * Показываем: `Желаемое окно клиента: 10:00 – 14:00` (из `windowStart` – `windowEnd`).
* **В карточке распределенной заявки (`status === 1`):**
  * В объекте остановки `stops` использовать точные поля:
    * **`serviceStart` – `serviceEnd`**: точный слот проведения работ (например: **11:15 – 12:15**).
    * **`estimatedArrival`**: расчетное время доезда к подъезду (например: **11:10**).
    * **`travelDurationMinutes`** и **`distanceFromPrevKm`**: время в пути и километраж (например: *25 мин, 4.2 км*).
    * `windowStart` – `windowEnd` клиента можно отображать мелким шрифтом рядом: *(в пределах окна клиента 10:00–14:00)*.

## 9. Симуляция течения времени (Time Slider & Playback)

**Задача UI:** В нижней части экрана разместить панель управления временем:
1. **Ползунок (Slider)** от `08:00` до `22:00`.
2. Кнопка **Play / Pause** с выбором скорости (`1x`, `5x`, `10x`).
3. Текущее выбранное время `T` (например, `13:45:00`).

### Реактивная смена статусов на карте (без запросов к бэкенду):
Фронтенд сравнивает текущее время ползунка `T` со временем остановок маршрута `stops`:
* **`T < stop.serviceStart`**: заявка запланирована на будущее → **Синий маркер** («Запланирована»).
* **`stop.serviceStart <= T <= stop.serviceEnd`**: инженер прямо сейчас выполняет заказ → **Пульсирующий оранжевый маркер** («В работе»).
* **`T > stop.serviceEnd`**: работы завершены → **Зеленый маркер с галочкой** («Выполнена»).
* **Позиция инженера:** если `stop[i].serviceEnd < T < stop[i+1].estimatedArrival`, инженер отображается как машинка/человечек на линии переезда («В пути»).

### Проброс времени в бэкенд (Action-триггеры):
При любых мутациях передавать текущее время `T` в Query-параметре `currentTime`:
* Отключение инженера: `PATCH /api/v1/engineers/{id}/availability?isAvailable=false&currentTime=2026-10-25T13:45:00Z`.
* Ручной реплан: `POST /api/v1/optimization/replan?currentTime=2026-10-25T13:45:00Z`.
* Аварийная заявка: `POST /api/v1/optimization/emergency` с телом `{ "eventTime": "2026-10-25T13:45:00Z", ... }`.

## 10. Виджет «Бизнес-эффективность» (KPI для жюри)

**Задача UI:** Дашборд/карточка в верхней панели, демонстрирующая экономическую выгоду решения относительно базового плана (Baseline).

* **Откуда брать данные:** Из поля `metrics` ответа оптимизации (`GET /api/v1/optimization/jobs/{jobId}/result`):
  ```json
  "metrics": {
    "totalOrders": 120,
    "assignedOrders": 118,
    "unassignedOrders": 2,
    "optimizedActiveEngineers": 8,
    "baselineActiveEngineers": 12,
    "savedEngineersCount": 4,
    "optimizedTotalDistanceKm": 142.3,
    "baselineTotalDistanceKm": 231.8,
    "distanceEconomyPercent": 38.6
  }
  ```
* **Что выводить на дашборде:**
  * 📉 **Экономия пробега:** `38.6%` (пробег `142.3 км` против базовых `231.8 км`).
  * 👥 **Высвобождено бригад:** `4 инженера` (работает `8` вместо `12`).
  * 🎯 **Покрытие заявок:** `98.3%` (`118 из 120` распределено).

## 11. Отображение обеденных перерывов (ТК РФ)

**Задача UI:** Показать в таймлайне инженера, что у него заложен обязательный перерыв на обед (45–60 мин) в середине дня.

* **Откуда брать данные:** В объекте маршрута каждого инженера `EngineerRouteDto` есть массив **`breakStops`**:
  ```json
  "breakStops": [
    {
      "start": "2026-10-25T13:00:00Z",
      "end": "2026-10-25T13:45:00Z",
      "durationMinutes": 45
    }
  ]
  ```
* **Как отображать:** В списке задач инженера между остановками отрисовать отдельную желтую плашку:  
  ☕ **Обед: 13:00 – 13:45 (45 мин)**.
