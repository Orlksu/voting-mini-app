# Планирование маршрутов выездных инженеров · Кейс 13, ЛЦТ 2026

Веб-сервис, который распределяет заявки между выездными инженерами (бригадами)
с учётом квалификации, смены, транспорта и временных окон, строит маршруты по
реальным дорогам Москвы, показывает их на карте и объясняет, почему заявка
досталась конкретному инженеру. При отмене, завершении или добавлении заявки
день автоматически перепланируется.

| Слой | Технологии |
|---|---|
| Frontend | React 19, Vite, MapLibre GL + MapTiler; раздаётся через Nginx |
| Backend | ASP.NET Core / .NET 10, EF Core, Google OR-Tools (VRPTW) |
| База данных | PostgreSQL 17 |
| Маршрутизация | Valhalla 3.5.1 (граф дорог из OpenStreetMap) |
| Геокодинг адресов | Nominatim (OpenStreetMap) |
| Запуск | Docker Compose |

## 🚀 Быстрый старт

Весь проект поднимается одной командой в Docker. Ничего, кроме Docker и Git,
ставить не нужно.

```bash
git clone <URL этого репозитория> case-13
cd case-13
./start.sh
```

`start.sh` проверит Docker и свободные порты, создаст `.env` из `.env.example`,
скачает и подготовит карту **Москвы и Московской области**, соберёт и запустит
все контейнеры, дождётся готовности сервисов и напечатает адреса. Скрипт ничего
не удаляет, его можно запускать повторно.

Вручную, без `start.sh` (граф будет **только по Москве** в пределах МКАД):

```bash
cp .env.example .env
docker compose up -d --build
```

### Windows

Запускайте из **WSL2** (Ubuntu) с включённой в Docker Desktop интеграцией
WSL (**Settings → Resources → WSL integration**). Клонируйте репозиторий
внутри WSL (например, в `~/`), а не в `C:\` — так быстрее и без проблем с
правами:

```bash
# в терминале Ubuntu (WSL)
git clone <URL этого репозитория> ~/case-13
cd ~/case-13
./start.sh
```

В Git Bash `start.sh` тоже запустится, но подготовку Московской области
пропустит (MSYS ломает пути в `docker run -v`) — граф будет только по Москве.
Из PowerShell работает ручной вариант `docker compose up -d --build`
(после `copy .env.example .env`), тоже только Москва.

Через 3–10 минут (зависит от скорости интернета) откройте
**<http://localhost:8080>**.

> Файл `.env` обязателен: в нём ключ карты MapTiler. Без него интерфейс
> откроется, но вместо карты будет надпись «Укажите VITE_MAPTILER_API_KEY».
> Ключ зашивается во frontend **при сборке**, поэтому если вы создали `.env`
> после первого запуска, пересоберите frontend:
> `docker compose up -d --build frontend`.

### Требования

| Что | Минимум |
|---|---|
| Docker | Docker Desktop (macOS / Windows) или Docker Engine (Linux) с Compose v2 — команда `docker compose` (через пробел) |
| Память для Docker | 6 ГБ, рекомендуем 8 ГБ (сборка графа Москвы с областью — пик ~3 ГБ) |
| Диск | ~7 ГБ (образы ~4,5 ГБ + выгрузка и граф Москвы с областью ~1,2 ГБ) |
| Интернет | нужен: скачиваются образы, карта Москвы OSM, подложка карты MapTiler и геокодинг Nominatim |
| Свободные порты | `8080`, `5001`, `5432`, `8002` |

Все образы мультиархитектурные: на Mac с Apple Silicon (M1–M4) и на Linux
x86_64 Docker сам берёт нативную сборку, эмуляция не нужна.

## ⏱️ Что происходит при первом запуске

1. **Сборка образов** frontend (`npm ci` + `vite build`) и backend
   (`dotnet publish`) и скачивание образов PostgreSQL и Valhalla — несколько
   минут, в основном время загрузки.
2. **Миграции БД** backend применяет сам при старте. База стартует **пустой**
   (данные загружаются через интерфейс, см. ниже).
3. **Граф дорог Valhalla.** `start.sh` скачивает выгрузки OpenStreetMap по
   Москве и Московской области (~300 МБ, openstreetmap.fr) и склеивает их
   в `valhalla-data/moscow_region.osm.pbf`, после чего Valhalla строит граф.
   Это самый долгий шаг: несколько минут на скачивание и склейку и ~4 минуты
   на сборку графа (замер на Apple Silicon, 4 потока, пик памяти ~3 ГБ).
   Без `start.sh` образ сам скачивает только Москву (~80 МБ, BBBike),
   граф собирается за ~2 минуты. Прогресс: `docker compose logs -f valhalla`.
   Готовность — строка про запуск `valhalla_service` в логах и ответ
   `curl http://localhost:8002/status`.

**Интерфейсом можно пользоваться сразу, не дожидаясь Valhalla.** Пока граф не
готов, backend оценивает расстояния по прямой (формула гаверсинуса). Статус `unhealthy` у `valhalla` в это время —
норма: healthcheck проверяет только готовность `/status`, контейнер при этом
не перезапускается. После готовности графа нажмите «распределить» ещё раз —
маршруты пересчитаются по дорогам.

Повторные запуски быстрые: граф сохраняется в `valhalla-data/`, база —
в Docker volume `postgres_data`.

## 🧭 Демо-сценарий

Все действия — в веб-интерфейсе <http://localhost:8080>.

1. **Бригады** → добавить инженеров: из CSV-файла или формой вручную.
   Адрес выезда инженера становится офисом (депо) на карте.
2. **Загрузить заявки** → «загрузить из файла (CSV)» или «ввести вручную».
   Адреса без координат геокодируются автоматически (Nominatim, нужен
   интернет; не быстрее 1 адреса в секунду из-за лимитов сервиса). Прогресс импорта
   виден в карточке задачи.
3. **Распределить** — запускает оптимизацию. Результат: маршруты инженеров
   на карте с номерами точек, метрики (назначено / не назначено, экономия
   пробега относительно базового плана) и причины назначения или отказа
   по каждой заявке. В меню рядом — «перераспределить все»: пересобрать
   маршруты, включая уже назначенные заявки.
4. **Текущие заявки** — список с поиском. В карточке заявки или в попапе на
   карте её можно **завершить** или **отменить**; при отмене маршрут
   инженера перепланируется автоматически.

### Формат CSV

Разделитель определяется автоматически (`;` или `,`), кодировка UTF-8.
Даты — московское время в формате `ДД.ММ.ГГГГ ЧЧ:ММ`.

**Заявки** (`загрузить заявки → из файла`):

```csv
Заявка;Адрес;Начало;Окончание;Тип заявки BK;Тип заявки HD;Район;Гигабит
Адрес Офиса;г. Москва, ул. 8 Марта, д. 10;;;;;;
TEST-001;г. Москва, ул. Тверская, д. 7;29.09.2026 09:00;29.09.2026 12:00;Локальная заявка;Ремонт;Тверской;Да
TEST-002;г. Москва, ул. Арбат, д. 25;29.09.2026 10:00;29.09.2026 13:00;Подключение;Подключение интернета;Арбат;Нет
```

| Колонка | Смысл |
|---|---|
| `Заявка` | внешний номер заявки |
| `Адрес` | адрес объекта; необязательные колонки `Широта` / `Долгота` отключают геокодинг |
| `Начало`, `Окончание` | временное окно визита |
| `Тип заявки BK` | определяет приоритет и длительность: `Авария`/`Глобальная` — 80 мин, `Подключение` — 60 мин, `Дозаказ` — 10 мин, остальное — 30 мин |
| `Тип заявки HD` | вид работ; вместе с `BK` определяет нужную квалификацию (аварийная / монтаж / локальный ремонт) |
| `Район` | район Москвы |
| `Гигабит` | `Да` — нужен инженер на автомобиле (везёт оборудование) |

Строка `Адрес Офиса;<адрес>` задаёт офис, к которому относятся заявки файла.

**Инженеры** (`бригады → из CSV`):

```csv
Код инженера;ФИО;Район;Адрес выезда;Широта;Долгота;Начало смены;Конец смены;Транспорт;Навыки;Лимит заявок
ENG-01;Иванов Иван;Тверской;г. Москва, ул. 8 Марта, д. 10;55.8003;37.5613;29.09.2026 08:00;29.09.2026 18:00;Авто;Монтаж, Ремонт, Аварийные;10
ENG-02;Петров Пётр;Арбат;г. Москва, ул. 8 Марта, д. 10;55.8003;37.5613;29.09.2026 09:00;29.09.2026 18:00;Общественный транспорт;Ремонт, Подключение;8
```

| Колонка | Значения |
|---|---|
| `Транспорт` | `Авто`, `Общественный транспорт`, `Велосипед`, `Пешком` (или `Car`, `PublicTransit`, `Bicycle`, `Pedestrian`) |
| `Навыки` | через запятую: `Монтаж`/`Подключение`, `Ремонт`, `Аварийные` (или `Installation`, `LocalRepair`, `Emergency`) |
| `Лимит заявок` | максимум заявок за смену, по умолчанию 15 |
| `Широта`, `Долгота` | необязательны: без них адрес выезда геокодируется |

Принимаются и английские заголовки (`ExternalId`, `Name`, `StartAddress`,
`ShiftStart`, …). Смена инженера должна пересекаться с окнами заявок — иначе
заявки останутся нераспределёнными с объяснением причины.

> Ставьте в CSV **сегодняшнюю или будущую дату**. «Распределить» планирует
> на дату ближайшей заявки, а автоматическое перепланирование (отмена,
> завершение, «перераспределить все») считает от текущего времени — заявки
> с прошедшими окнами останутся нераспределёнными.

## 🛠️ Если что-то пошло не так

| Симптом | Причина и решение |
|---|---|
| Вместо карты надпись «Укажите VITE_MAPTILER_API_KEY» | Нет `.env` при сборке. `cp .env.example .env`, затем `docker compose up -d --build frontend` и обновить страницу с очисткой кэша (Ctrl/Cmd+Shift+R) |
| `Bind for 0.0.0.0:5432 failed: port is already allocated` (или 8080 / 5001 / 8002) | Порт занят, часто локальной PostgreSQL. Остановите её или поменяйте левую часть маппинга в `docker-compose.yml`, например `"15432:5432"` |
| `Conflict. The container name "/lct-db" is already in use` | Остался контейнер от прошлого запуска из другой папки. `docker rm lct-db lct-valhalla` (данные БД лежат в volume и не удаляются) |
| `valhalla` в статусе `unhealthy` | Во время первой сборки графа — норма, см. «Что происходит при первом запуске». Приложение работает |
| `valhalla` перезапускается, в логах `Killed` | Не хватило памяти при сборке графа. Увеличьте память Docker Desktop до 8 ГБ или добавьте в `.env` строку `VALHALLA_SERVER_THREADS=2`. Затем отложите недособранный граф — `valhalla-data/valhalla_tiles`, `valhalla_tiles.tar`, `file_hashes.txt` — в другую папку (`moscow_region.osm.pbf` оставить) и выполните `docker compose up -d --force-recreate valhalla`. Подробно — [docs/valhalla.md](docs/valhalla.md) |
| Заявки импортируются с `unresolvedAddresses` | Nominatim не нашёл адрес или недоступен. Проверьте интернет или добавьте в CSV колонки `Широта` / `Долгота` |
| Страница открылась, но API отвечает 502 | Backend ещё стартует или упал: `docker compose logs backend` |

Логи любого сервиса: `docker compose logs -f <frontend|backend|db|valhalla>`.

## 🗺️ Граф Москвы с областью

`start.sh` готовит Москву с областью сам, если каталог `valhalla-data/` пуст
(первый запуск). Если там уже лежит граф только по Москве, скрипт его не
трогает и предупреждает. Как перейти на Москву с областью, не потеряв старый
граф, и как откатиться, описано в [docs/valhalla.md](docs/valhalla.md);
выгрузку готовит `scripts/prepare-valhalla-region.sh`.

## 💻 Запуск без Docker (для разработки)

Нужны Node.js 20+, .NET 10 SDK и PostgreSQL / Valhalla (удобно поднять только
их: `docker compose up -d db valhalla`).

```bash
# backend → http://localhost:5077
ConnectionStrings__DefaultConnection="Host=localhost;Port=5432;Database=lctdb;Username=user;Password=password" \
Valhalla__BaseUrl="http://localhost:8002" \
ASPNETCORE_ENVIRONMENT=Development \
dotnet run --project backend/src/Backend.Api

# frontend → http://localhost:5173
cd frontend
cp .env.example .env.local   # вписать VITE_MAPTILER_API_KEY и VITE_API_URL=http://localhost:5077/api/v1
npm ci
npm run dev
```

Проверки, которые запускает CI:

```bash
cd frontend && npm ci && npm run lint && npm run build
dotnet build backend/src/Backend.Api/Backend.Api.csproj --configuration Release
```

## 🔁 CI/CD и staging

Конфигурация SourceCraft Pipelines — `.sourcecraft/ci.yaml`. При каждом push
в `develop` pipeline:

- запускает `npm ci`, lint и production build frontend;
- собирает backend через .NET 10 SDK;
- подключается по SSH к staging VM, получает `origin/develop` и выполняет
  `docker compose up -d --build` с `docker-compose.staging.yml`;
- проверяет backend `/healthz` и HTTP-ответ frontend.

В staging PostgreSQL и Valhalla наружу не публикуются. На VM один раз
подготовьте репозиторий в `~/case-13-field-engineer-routing-team-97`,
установите Docker Compose plugin, Git и curl и создайте `.env.staging`
по шаблону `.env.staging.example`.

Секреты репозитория SourceCraft:

| Secret | Значение |
|---|---|
| `STAGING_HOST` | DNS-имя или IP staging VM |
| `STAGING_USER` | SSH-пользователь |
| `STAGING_SSH_PRIVATE_KEY` | приватный SSH-ключ pipeline |
| `STAGING_KNOWN_HOSTS` | строка из `ssh-keyscan` для VM |
